# CLAUDE.md

Operating instructions for Claude Code in this repository. Read `PROJECT_CONTEXT.md` first for the full spec — this file is about *how to work*, not *what to build*.

## Project in one line
Vision-based adaptive traffic signal control on a fully synthetic city: a fake road network in SUMO generates realistic time-of-day traffic (peaks ~9am/~6pm) → noisy vehicle counts get smoothed into stable density estimates → a queue-proportional controller allocates green time per approach → validated across varying volumes, all inside SUMO. YOLOv6 detection is a separate proof-of-concept layer (runs on rendered simulation frames), not a hard dependency of the main control loop.

## Status
Rebuilding from scratch. Original team-project code was lost; nothing here should be assumed to exist until it's actually in the repo. Do not reference or reconstruct "previous" implementation details — treat this as a greenfield build guided by the spec in PROJECT_CONTEXT.md. No real camera feed is available or needed — everything below is synthetic/simulated.

## Repo layout
```
src/citygen/      - fake road network definition + time-varying demand generator (peak-hour curve)
src/detection/    - YOLOv6 wrapper; proof-of-concept only, runs on rendered sim frames, not wired into main loop by default
src/smoothing/    - temporal filtering (raw counts -> stable density estimate)
src/controller/   - green-time allocation logic (density -> signal timing)
src/sim/          - SUMO/traci bridge, scenario runners, ground-truth queue readout
sumo_scenarios/   - .net.xml, .rou.xml, .sumocfg (generated by src/citygen, not hand-authored)
external/YOLOv6/  - vendored upstream repo, do not modify
tests/            - one test module per src/ subpackage, mirrored structure
configs/          - YAML configs (demand curve params, network topology, controller constants)
```

## Build order (follow this sequence; don't jump ahead)
1. `src/citygen` — define a small fake road network (start with a single 4-way signalized intersection, or a 2x2 grid if time allows) and a demand generator that produces SUMO route/flow files with a time-varying rate: low overnight, ramping to a peak around 9am, dipping midday, ramping to a second peak around 6pm. Sanity-check the generated demand curve with a plot before moving on.
2. `src/controller` — pure function(s): density estimates in, green-time-per-approach out. No I/O, no SUMO/traci dependency. Fully unit-testable with synthetic inputs.
3. `src/smoothing` — implement and unit-test the smoothing filter on synthetic noisy count sequences.
4. `src/sim` — traci bridge: read ground-truth per-approach queue/vehicle counts from SUMO each cycle, run them through smoothing → controller, apply the resulting green times back to the simulation. This is the primary end-to-end loop and it should work with ground-truth counts alone, with no detection involved.
5. `src/detection` — proof-of-concept, built after step 4 works: capture rendered frames from the running simulation (sumo-gui screenshot or a recorded video of a run) and run YOLOv6 on them to detect/count vehicles per lane ROI. Compare detection output against the traci ground truth from the same timestep as a rough accuracy check. This module demonstrates the vision piece is implementable; it does not need to replace the ground-truth counts in the main loop unless there's time to integrate it properly.

Do not start step N+1 until step N has passing tests and a runnable example.

## Conventions
- Python 3.10, type hints on all public functions.
- Controller logic (`src/controller`) must stay side-effect-free and simulator-agnostic — it should be testable with plain dicts/arrays, no traci imports. This is the piece most likely to get reused or swapped out; keep it decoupled.
- Config via YAML in `configs/`, loaded once, passed explicitly — no global state, no reading env vars deep in the call stack.
- Every new module in `src/` gets a corresponding test in `tests/` before being wired into the pipeline.
- Commit granularity: one logical change per commit (e.g. "add per-lane count smoothing filter", not "wip" or "updates").

## When implementing
- Ask before choosing the smoothing method (moving average vs exponential vs Kalman) if it's not already decided in PROJECT_CONTEXT.md — this is a real design decision, not a detail to default silently.
- Ask before choosing the green-time allocation formula (e.g. straight proportional split vs proportional with a minimum floor per approach) for the same reason.
- Ask before finalizing the road network topology and the demand-curve shape/parameters (peak height, peak width, per-approach imbalance) — these define what "realistic traffic" means for this project and are worth a deliberate choice, not a default.
- Prefer clarifying questions over silent assumptions for anything that affects the controller's actual traffic behavior — this is the part graders/reviewers will scrutinize.
- Everything else (file structure, helper naming, test scaffolding) — use best judgment, no need to ask.

## Running things
- Install: `pip install -r requirements.txt` (`eclipse-sumo` bundles the SUMO binaries + sumolib/traci; `src/sumo_env.py` locates them, honouring `SUMO_HOME` if set).
- Unit tests: `pytest tests/`
- Build a scenario: `python -m src.citygen --network configs/network_eixample.yaml --demand configs/demand_balanced.yaml` → `sumo_scenarios/eixample_3x3__balanced.sumocfg` (+ `.net.xml`, `.rou.xml`, `.tls.add.xml`). Network configs: `network_single.yaml` (1 intersection), `network_eixample.yaml` (3x3). Demand configs: `demand_{light,balanced,imbalanced,heavy}.yaml`.
- Plot a demand profile vs. sampled departures: `python scripts/plot_demand.py --network <net.yaml> --demand <demand.yaml>`
- SUMO GUI run (for visual sanity check): `sumo-gui -c sumo_scenarios/<scenario>.sumocfg` (runs the fixed 20 s per-approach baseline program `per_approach`; phases are named `N_green`, `N_yellow`, `N_allred`, `E_green`, … so `src/sim` can address approaches by name)
- Headless SUMO + traci control loop: `python -m src.sim --scenario sumo_scenarios/eixample_3x3__balanced.sumocfg --control adaptive` (`--control fixed` = baseline with identical logging, `--no-smoothing` = raw counts into the controller, `--gui`, `--begin/--end` seconds to run a window, `--aggregate instant|cycle_max|cycle_mean`, `--noise configs/noise_detector.yaml` for synthetic detector noise on the counts). Outputs `<run>_cycles.csv` (per junction per cycle: raw, smoothed, green per approach), `_stats.json`, `_tripinfo.xml`, `_summary.xml` in `sumo_scenarios/output/`.
- Detection PoC: `python -m src.detection capture --scenario <sumocfg> --tls <junction> --begin <s> --frames N` (sumo-gui frames + ground truth + auto-labels) and `python -m src.detection evaluate --weights <ckpt> --annotate` (detected vs. truth per approach). Dataset + fine-tune: `python scripts/build_detection_dataset.py`, then YOLOv6's `tools/train.py` with `PYTHONPATH=external/YOLOv6 TORCH_FORCE_NO_WEIGHTS_ONLY_LOAD=1` and `configs/yolov6n_sim_finetune.py` (see README). Capture gotchas: sleep ~2 s after `traci.start` before the first screenshot or the step blocks forever; screenshots are rendered at the on-screen *vertical* scale (`ViewTransform.from_screenshot`); the PNG is written asynchronously — wait for it to decode before reading.
- Validation matrix (profiles x modes, writes `sumo_scenarios/output/experiments_<network>.md`): `python scripts/run_experiments.py --demands light balanced imbalanced heavy --modes fixed adaptive adaptive_nosmooth`. Full-day 3x3 runs take ~5-20 min each; use `--begin/--end` for quick checks.

## Do not
- Do not vendor changes into `external/YOLOv6/` — wrap it from `src/detection` instead.
- Do not hardcode SUMO_HOME or absolute paths — read from env/config.
- Do not add a hardware/live-camera deployment layer — there is no camera feed, real or planned; everything is SUMO-simulated.
- Do not make the main control loop (`src/sim`) depend on `src/detection` succeeding — ground-truth traci counts must remain a fully working path on their own.
